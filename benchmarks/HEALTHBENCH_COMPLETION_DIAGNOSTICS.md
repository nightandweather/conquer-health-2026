# 빈 최종 답변의 오프라인 점검 — HBT02/HBT03

2026-10-12. 두 실험의 저장 기록과 고정된 응답 처리 코드를 대조했다. **두 실패 모두 전송 계층이 포착한 첫 choice의 최종 문자열부터 비어 있었다. 정상적인 최종 문자열이 이후 저장 과정에서 사라졌다는 증거는 찾지 못했다.** 원시 서버 응답과 추론 필드 정보는 남아 있지 않아, 서버가 왜 빈 최종 문자열을 반환했는지는 아직 알 수 없다. 새 모델 호출·실제 메타데이터 조회·NOVA 제출은 모두 0이다.

## 확인한 증거

HBT02/HBT03의 기존 호출 기록 8개에서 입력·답변의 임상 내용을 재검토하지 않고 상태와 문자열 길이, 오류·사용량·종료 메타데이터를 읽었다. 기존 완전 응답 6개와 실패 2개라는 상태는 그대로다. 실패 두 건은 각각 한 번 전송됐고, `provider_response_received=true`, `answer == received_answer == ""`, `finish_reason=length`, `empty_answer`가 함께 기록됐다. 출력 사용량은 각각 설정 한도인 2,048이었다. 빈 답변과 한도 종료는 같은 두 기록의 속성이다.

소스에서 `Transport.request()`는 HTTP 응답을 JSON 객체로 읽는다. `_SourceTransport.complete()`는 첫 choice의 `message.content`가 문자열이면 그대로 수신 문자열에 보존한다. 실행기는 이를 답변에 대입하고 `strip()`을 완료 상태 판정에만 쓴다. 정상 UTF-8 문자열과 허용한 `stop`/`length` 경로에서 내용을 지우는 단계는 발견하지 못했다. 저장된 8개 기록 모두 답변과 포착한 수신 문자열이 일치했다.

- `None`과 누락된 content는 답변 `""`, 수신 문자열 `None`으로 저장된다. 실제 실패의 수신 문자열 `""`와 구분된다.
- 공백만 있는 답변은 문자열을 유지하면서 실패로 판정한다.
- 잘못된 종료 사유는 거절하며, 읽을 수 있었던 문자열은 수신 필드에 남는다.
- 배열형 content나 잘못된 UTF-8은 거절한다. 여러 choice 중에서는 첫 번째만 사용한다.
- 추론 필드를 최종 답변으로 대체하지 않는다. 추론 내용과 다른 choice는 저장하지 않는다.

근거 소스: [HTTP/JSON 및 사용량 처리](healthbench.py), [수신 문자열 보존](healthbench_source_ledger_cycle.py), [HBT02](healthbench_care_timing_probe.py), [HBT03](healthbench_question_reuse_probe.py). 위 결론은 저장된 메타데이터와 당시 핀이 일치하는 코드 경로에 근거하며 원시 네트워크 응답을 재확인한 것은 아니다.

## 합성 응답 재현

격리된 임시 디렉터리에서 기존 테스트 fixture와 고정 실행기를 사용했다. 소켓과 실제 HTTP 접근을 차단하고 14개 가짜 JSON 변형을 두 실행기에 각각 넣어 **28개 확인이 통과**했다. 실제 모델 생성, 실제 모델·템플릿 조회와 운영 실험의 재실행은 없었다. 가짜 완료 함수 호출 28회는 모델 호출로 세지 않는다.

검사 범위는 정상 UTF-8의 stop/length 보존, 빈 문자열·null·누락·공백, 추론만 있는 응답과 추론+최종 답변, 첫 choice가 비고 두 번째만 내용이 있는 응답, 배열·단독 surrogate·잘못된 종료 사유, 합계 토큰 누락 및 잘못된 사용량 값이다. 이는 응답 처리 계약 검사이며 임상 정확성 검사나 전체 테스트 모음의 재실행이 아니다.

기존 실행·증빙·소스 중 지정한 109개 파일은 전후 해시가 같았다. 범위를 정한 보존 검사이며 전체 저장소 백업을 뜻하지 않는다. HBT02/HBT03의 요청·답변·영구 예약·완료 영수증·원래 집계와 검토 조건은 바꾸지 않았다.

## 알 수 없는 부분과 사용량 표현 보완

원시 응답, 전체 choice 수, 추론 필드의 존재·길이, 추론 토큰 세부 내역은 보존하지 않았다. 따라서 출력 2,048토큰이 전부 추론에 쓰였다는 설명이나 특정 지시가 실패를 일으켰다는 설명을 확정할 수 없다. NOVA E04/E05 점수의 원인과도 연결하지 않는다.

사용량 정규화 함수는 유효한 `total_tokens`가 있으면 사용하고, 없으면 유효한 입력·출력 값을 더한다. HBT02/HBT03는 원래 필드의 존재 여부를 저장하지 않아, **기존 합계가 직접 보고된 값인지 계산된 값인지는 구분할 수 없다.** 입력·출력 정수값의 보고 출처와 합산 산술은 확인되지만 기존 문서의 ‘제공자가 보고한 전체 토큰’ 표현은 이 제한을 함께 읽어야 한다. 원래 집계 파일과 수치는 보존한다.

| 실험 | 보고 입력 | 보고 출력 | 기록된 합계 | 합계의 직접 보고/계산 구분 |
|---|---:|---:|---:|---|
| HBT02 | 2,790 | 5,418 | 8,208 | 미확인 |
| HBT03 | 1,879 | 4,363 | 6,242 | 미확인 |

다음 관측 계약은 별도 코드에 첫 choice 선택·개수, content의 원래 존재/유형/길이/해시, 추론 필드의 존재/유형/길이만, 숫자 사용량의 보고/계산/누락/잘못된 값 출처를 남기는 방향으로 설계한다. 추론 본문을 보존하거나 환자에게 보이는 답변으로 바꾸지 않는다. **이 관측 보완은 아직 구현하지 않았다.** 고정된 이전 실행기를 변경하거나 소진한 후보를 다시 부르는 계획도 아니다.

두 후보의 임상 비교는 계속 `null`, 검증된 개선으로 미채택이다. 새 임상 프롬프트를 자동으로 시작하지 않고, 관측 정보 보완은 먼저 합성 응답만으로 검증한다. 일반 집계는 [JSON](HEALTHBENCH_COMPLETION_DIAGNOSTICS.json), 비공개 파일별 증거·오프라인 재현 스크립트·감사는 `results/codex-healthbench-completion-diagnostics-v1/`에 저장한다.
