# NOVA 외부 자료 활용 · 오프라인 검색 계획

2026-10-12 공식 문서 확인. 실행 구현·임상 성능 검증·채택을 뜻하지 않습니다.

## 확인된 실행 조건

제출하는 추론 코드에서는 외부 API를 호출할 수 없습니다. 연구 출판에 사용할 수 있는 라이선스의 외부 데이터·모델·도구는 출처와 처리 과정을 명시해 사용할 수 있습니다. 자료를 개발 단계에서 확보하고 실행 중 로컬 파일로 검색하는 구성이 해당 조건에 맞습니다. 각 자료의 이용·재배포 조건은 별도로 확인해야 합니다. [공식 Q&A](https://nova.snubhai.org/qna/), [참가 규칙](https://nova.snubhai.org/rules/)

`prepare()`를 포함한 실행 중 인터넷은 차단되며 지정 대회 API만 허용됩니다. 예선은 고정 `gpt-oss-20b`를 증례마다 최소 한 번 사용해야 합니다. 다른 외부 생성 모델로 답변을 대신 만들 수 없습니다. 정적 검색 인덱스와 CPU용 보조 임베딩 자산은 제출·실행 한도 안에서 사용할 수 있습니다. [참가 규칙](https://nova.snubhai.org/rules/)

운영진의 진료지침 15,904개는 `/opt/nova/guidelines`에 읽기 전용으로 제공되며 `NOVA_GUIDELINES_DIR`에서 경로를 받습니다. 코드 ZIP에 원문을 넣을 필요는 없습니다. 개발용 ZIP을 포함한 공식 파일 6개를 이 작업에서 수령·검증했고, 전체 지침의 로컬 색인과 원문 조회를 구현했습니다. 실제 진료 에이전트 적용과 임상 검색 성능은 아직 검증하지 않았습니다. 문서별 출처·라이선스를 유지해야 하고 변경본 배포가 금지된 자료도 있습니다. [개발 가이드](https://nova.snubhai.org/docs/)

## 루닛에서 검토한 구성의 적용 방향

| 자료 | NOVA에서 검토할 경로 | 현재 상태 |
|---|---|---|
| 진료지침 | 운영진 제공 파일에서 증상·문진·진찰·치료 근거 검색 | 전체 로컬 색인·조회 구현, 진료 에이전트 연결 전 |
| MFDS·e약은요·DailyMed | 이용 조건 확인 후 약품명·성분·주의사항의 버전 고정 로컬 데이터 | 수집·라이선스·연결 미확인 |
| HIRA·KCD·법령 | 필요한 경우 급여·코드·조문을 출처와 함께 로컬 조회 | 적용 필요성·이용 조건 미확인 |
| PubMed·FAERS | 공개 조건에 맞는 범위만 로컬 문헌·자료 검색 | 수집·해석·연결 미확인 |

루닛 MCP 서비스의 접근권한이나 그 서비스가 제공했던 코퍼스를 NOVA에서도 사용할 수 있다는 뜻은 아닙니다. API 목록과 당시 검색 체인은 [루닛 설계 문서](https://github.com/Hackathon-AIM/health-conquer-submission/blob/lunit/hackathon-submission/docs/l2_playbook.md)에 기록돼 있습니다.

## 다음 구현과 검증 범위

개발 단계 자료 확보 → 출처·버전·해시를 고정한 로컬 색인 → 질문에 맞는 짧은 근거 검색 → 지정 gpt-oss에 근거와 환자 정보를 구분해 전달하는 흐름을 검토합니다. 기존 `nova/core.py`에는 검토된 지식 카드의 단어 겹침 검색이 있지만 현재 `run.py`와 연결돼 있지 않고 임상적으로 검증된 검색기가 아닙니다. 별도의 `nova/guidelines.py`와 `nova/guideline_context.py`에서 제공 지침의 원문 조회와 입력 초안 생성이 작동합니다.

먼저 제공 지침을 사용하는 좁은 오프라인 검색과 인터넷 없는 준비 시험을 검증합니다. 일반 지침의 내용을 환자에게서 확인된 소견으로 기록하지 않아야 합니다. 모델이 자료를 읽었다는 이유만으로 사실 오류·반복 질문·최종 기록 오류가 해결됐다고 판단하지 않습니다.

HealthBench 개발 실험에 연결한다면 입력·설정·모델·대조군을 고정하고 검색 근거 추가만 바꾸는 별도 비교 경로가 필요합니다. 이번 회차의 생성 한도는 이미 사용했으므로 추가 호출하지 않았습니다. 기존 평가용 180문항의 개별 피드백을 검색·프롬프트 수정에 사용하지 않습니다. 새로운 원문·색인 경로와 실제 NOVA 여러 턴 검증이 준비될 때까지 적용·개선·제출 완료를 주장하지 않습니다.

## API 조회에 가까워지기 위한 기능과 성공 기준

| 기능 | 구현 방향 | 검증할 기준 |
|---|---|---|
| 약품·성분·코드 조회 | 고유 ID와 버전이 있는 로컬 DB의 필드를 그대로 반환 | 같은 원본 버전의 선택 필드가 원문과 일치; 모호한 이름·없는 항목은 미확인 |
| 진료 근거 검색 | 지침에서 필요한 구절과 문서 ID·출처·버전을 반환 | 필요한 근거의 검색 누락과 잘못된 인용을 독립적으로 측정 |
| 환자 사실 보존 | SAY·EXAM 응답과 턴 번호를 원장에 저장 | 검색 문헌·가설·미확인 사항이 환자 소견으로 승격되지 않음 |
| 최종 기록 검사 | 식별자·수치·단위·출처·확인 여부를 코드로 검사 | 변경된 값·존재하지 않는 참조·미확인 소견의 확정 기록을 거부 |

정확한 필드 조회는 같은 원본 버전의 항목으로 원문 일치율 100%를 목표로 검증할 수 있지만, 실시간 API의 최신 자료·전체 검색 범위·답변 품질과 동일하다는 뜻은 아닙니다. 별칭 처리와 근거 선택은 따로 검증해야 합니다. 조회 자료를 모델이 임의로 바꿔 쓰지 않게 하고, 해석이 필요한 내용은 원문과 구분합니다. 코드 검사도 모든 의학적 오류를 검출하지는 못합니다.

HealthBench 질문·답변·평가 기준을 정답 조회용 자료나 검색 색인으로 넣지 않습니다. 일반 공개 자료와 운영진 제공 지침만 적절한 조건으로 사용하고, 기존 개발 20개와 다른 독립 평가가 필요하면 새 데이터 범위부터 명시합니다. Codex는 개발 검증자이며 제출 실행에는 검색·원장·코드 검사와 허용된 Doctor 호출만 들어갑니다. 전체 답변 품질·새 중대한 오류·누락·반복·시간·토큰을 확인한 후에만 채택을 판단합니다.

## 현재 로컬 문서와 공식 웹의 차이

현재 공식 규칙의 진료 제한은 30분이고, 10월 10일 확보한 시작 패키지 설명은 20분입니다. 수령한 공식 SDK 1.0.1이 `reasoning_effort`·`temperature`·`model` 전달과 User-Agent 헤더를 실제로 지원함을 확인했습니다. 현재 root SDK는 보존한 1.0.0이고, 별도 제출 후보에는 최신 공식 SDK와 같은 배포의 기본 에이전트를 함께 사용했습니다. 기존 로컬 실행·HealthBench 결과의 조건은 그대로 보존하고, 다음 제출 적용 전에 최신 공식 패키지와 서버 샘플로 계약을 확인해야 합니다. 이 문서 확인만으로 SDK나 타이머를 변경하지 않았습니다.
