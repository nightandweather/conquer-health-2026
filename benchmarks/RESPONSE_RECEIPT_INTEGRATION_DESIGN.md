# 응답 메타데이터 연결 계약 — 미실행 설계

## 연결 위치와 관측 범위

현재 `_SourceTransport.complete()`는 내부 `client.complete()`가 반환한 객체를 의미 검사하고, 그 뒤에 실행기가 영수증을 쓴다. 앞으로 별도 어댑터를 만든다면 **반환된 객체 → helper → 구조 영수증 저장 → 의미 검사** 순서여야 한다. helper에 준 원래 객체를 수정하지 않고 같은 객체를 검사기에 넘긴다. 다른 choice나 추론을 답변으로 대체하지 않는다.

이 위치에는 한계가 있다. 현재 `Transport.request()`는 JSON을 해석한 뒤 비객체와 error 응답을 먼저 거절한다. 이 계층 위의 관측은 그 함수가 실제로 반환한 객체에 한정된다. 합성 검사에 잘못된 객체를 직접 넣더라도 실제 HTTP 응답의 관측 범위를 넓혔다고 볼 수 없다. 원시 HTTP 바이트나 과거 소실된 필드를 복구하지 않는다. 근거: [Transport](healthbench.py), [의미 검사](healthbench_source_ledger_cycle.py), [고정 실행기](healthbench_question_reuse_probe.py).

## 제안하는 영수증 순서

1. 고정 owner와 fixture 범위, 요청·fixture·helper·parser 핀 및 모의 신원 검사를 확인한다.
2. 영구 예약을 독점 생성하고 저장한다. 이 시점부터 해당 슬롯은 소비된다.
3. 예약 해시를 연결한 ‘전송 가능성’ 표식을 영구 저장한다. 이 표식은 실제 호출·응답 수신의 증명이 아니다.
4. 등록된 fake dispatch를 최대 한 번 호출한다.
5. 객체 반환을 메모리에서 관측하고, 의미 검사 전에 helper의 구조 메타데이터를 만든다.
6. 구조 영수증을 독점 생성하고 파일·디렉터리 저장 경계와 스냅샷을 확인한다.
7. 구조 저장이 끝났을 때만 같은 원래 객체를 의미 검사기에 넘긴다.
8. 후속 핀을 모의 확인하고 예약·전송 가능성·구조 영수증·핀 결과 해시와 정제한 처리 결과를 완료 영수증으로 연결한다.

후속 구현은 새 파일과 임시 합성 디렉터리에 한정하며 실제 endpoint/key/model transport 경로를 제공하지 않는다. 기존 HBT 실행기·helper·영구 예약 및 E05 코드는 변경하지 않는다. 실제 모델에 연결하는 작업은 이번 범위에 포함되지 않는다.

## 중단·실패를 구분하는 계약

`parsed_object_observed`, `structural_receipt_persisted`, `parser_entered`, `terminal_receipt_persisted`와 의미 검사 결과를 별도로 둔다. 구조 저장 실패는 모델의 임상 실패나 제공자 미응답이 아니다. 기존 상위 transport는 반환 전 예외를 미수신으로 처리할 수 있으므로, 이 별도 상태가 필요하다.

구조 저장에 실패하면 의미 검사 진입을 막는다. 가능할 때 고정 stage/code와 실제 관측 상태만 별도 실패 영수증에 기록한다. 그 저장도 실패했다면 디스크에 남은 이전 증거만 사용한다. 재시작 시 누락된 수신 증거는 false가 아닌 unknown이다. 완료 영수증의 존재만으로 답변 성공을 인정하지 않는다.

예약 이후 중단은 fake 호출 카운터가 실제로 0이었던 시험에서도 재전송 권한을 돌려주지 않는다. 같은 요청을 다른 출력 폴더에서 다시 시작할 수 없다. 부분 파일, 고아 증거, 해시 불일치, symlink, 기존 파일 충돌, 남은 잠금은 차단 사유다. 원래 파일을 지우거나 덮어써 복구하지 않고 자동 잠금 해제도 하지 않는다. 파일·디렉터리 fsync 순서는 후속 장애주입 검사의 대상이며 모든 저장장치의 전원 차단 내구성을 보증하지 않는다.

오류 메시지·예외 문자열·traceback·임의 클래스명·경로·식별자·답변/추론 본문을 기록하지 않는다. helper가 허용한 구조와 숫자 출처만 보존한다. content 해시도 익명화는 아니므로 향후 실제 개별 영수증은 계속 비공개다.

각 시험은 새 합성 scope를 사용하며 예약당 fake 호출 최대 1회를 확인한다. 실제 HBT owner와 예약을 초기화하지 않는다. fake 호출 총수와 실행 시간은 후속 구현 결과에서 별도 집계한다. 실제 생성·모델/템플릿 조회·제출 계획은 0회이며 작업 시간·비용 추정치는 아직 없다. G14는 합성 적격 표시만 확인하고 실제 맹검 자료를 내보내지 않는다.

HBT02/HBT03의 기존 네 완전 답변 검토 조건·재시도 금지·임상 비교 null·미채택을 유지한다. 이 설계는 빈 답변 원인 규명이나 임상 개선의 증거가 아니다. 구조화된 계약은 [JSON](RESPONSE_RECEIPT_INTEGRATION_DESIGN.json), 비공개 설계 검증과 게시 영수증은 `results/codex-response-receipt-integration-design-v1/`에 저장한다.
